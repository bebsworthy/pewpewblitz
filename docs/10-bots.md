# Bots

## Status

Player bots are a **v2-or-later candidate**. This document records the architectural direction and
the contracts that a future milestone must validate; it does not assign bots to a milestone or
authorize production implementation in the current v1 scope. Milestone placement, detailed balance
values, and delivery planning wait until a future version is scoped.

## Decision

Bots that fill in as players are **external clients**, not server-internal entities and not a
separate offline simulation. A bot runs the existing client application in a dedicated headless bot
mode: it connects over the real network transport, joins, selects a build, readies, and plays the
match by sending ordinary `FighterInput` intent through the same validated path as a human player.
The dedicated server grants a bot no special authority and contains no bot-specific simulation path.

This decision was reached after comparing three approaches:

1. **Server-internal bots** — the server writes `FighterInput` for fighters without a connection.
   This is cheapest per tick and easiest to make deterministic, but it gives the policy direct access
   to authoritative state and requires a second input-ownership path.
2. **External client bots (chosen)** — a bot is an ordinary client whose input is generated by a
   policy instead of a device. This preserves the network-first product boundary:
   - the official bot receives only state replicated to its observer connection;
   - ownership, finite/range/rate, sequence, and freshness validation remain identical to other
     clients;
   - server-owned movement, combat, abilities, modes, scores, respawns, and victory remain unchanged;
   - a later learned or non-Rust policy can integrate without adding a privileged game-server path.
3. **Learned policies (ML/imitation)** — deferred. There is no replay dataset, gameplay is still
   evolving, and the product values readable combat over optimal play. The observation and decision
   contracts below keep this option open without optimizing the first implementation around it.

External-client architecture provides **authority and information-boundary equivalence**, not
automatic perceptual or skill fairness. An official bot can still exploit exact replicated values
more effectively than a human, and any modified client can still send hostile traffic. The server
must continue treating all clients as untrusted; bot fairness comes from the explicit perception and
tuning contracts below.

## First-version scope

- **CLI launch.** A bot is started explicitly or through a thin process-launch recipe. There is no
  lobby fill detection, matchmaking, backfill, or server-side subprocess orchestration.
- **One validated behavior profile.** There are no player-facing difficulty presets or skill
  ranking. The target is fun, readable opposition: imperfect aim, bounded reaction delay,
  telegraphed commitments, and no perfect projectile tracking.
- **Current built-in modes and builds.** The policy must use mode goals and resolved build
  capabilities rather than preset-specific branches, so support can grow without replacing the
  policy boundary.
- **Seeded policy traces.** Given the same versioned profile and the same canonical ordered
  observation stream, the policy must produce the same decisions. A wall-clock external network
  session is not promised to reproduce tick-for-tick because replication arrival and impairment are
  inputs to that observation stream.

## Runtime shape

```text
observer-specific replicated client World
  -> bounded observation adapter
  -> canonical owned BotObservation
  -> mode goal + deterministic navigation
  -> utility policy + committed tactic state
  -> BotDecision
  -> existing PendingLocalActions / Lightyear input writer
  -> network -> server validation -> authoritative simulation
```

Join, compatibility, build selection, readiness, input transport, combat, scoring, and replication
remain ordinary client/server behavior. Substantial bot code is expected in observation extraction,
navigation, policy evaluation, lifecycle integration, diagnostics, and verification; it must not be
accumulated inside the existing `apply_headless_input` automation system.

## Perception contract

The bot policy must not query arbitrary ECS state. A client-owned adapter constructs an **owned,
bounded, canonical** `BotObservation` from an allowlist of facts available to that observer:

- match ID, mode, phase, objective state, and latest observed authoritative tick;
- the controlled fighter's stable ID, team, pose, health, resolved public build capabilities,
  weapon/ability state, defeat/respawn state, and protection state;
- visible fighters with stable ID, team, pose, public combat state, and observation age;
- visible projectiles and deployables with stable identity, public trajectory/owner facts, pose, and
  observation age;
- the validated resolved map bounds and collision-relevant geometry;
- explicit staleness and completeness indicators.

Collections are sorted by stable network, projectile, deployable, placement, or definition IDs
before policy evaluation. Process-local Bevy `Entity` values, presentation-only components, raw ECS
queries, private server state, and unbounded message history never cross the policy boundary.

The observation allowlist is also the future concealment boundary. If network visibility removes an
entity for this observer, it cannot appear in the observation. Public roster information must not be
silently promoted into live spatial knowledge. When concealment is implemented, packet/application
tests must prove that hidden state and subject-derived private messages cannot enter bot perception.
The same observation adapter may later consume an explicitly visibility-filtered in-process test
view, but it must never read the complete authoritative `World` directly.

## Tick and schedule contract

Bot decisions are tied to **observed authoritative progress**, not render frames or the number of
local catch-up ticks:

1. After Lightyear replication and pose interpolation have completed, assemble the latest coherent
   observation into a client-owned resource.
2. Before `InputSystems::WriteClientInputs`, evaluate the policy at most once for each new observed
   authoritative tick/generation.
3. Reuse the last decision when multiple local fixed ticks run without a newer observation. Do not
   consume more randomness or decrement reaction/commitment timers for duplicate observations.
4. Express reaction, commitment, cooldown-estimation, and stale-observation deadlines in observed
   authoritative ticks. If the observation exceeds the profile's staleness limit, emit neutral
   input until a fresh generation arrives.
5. Keep ordering against replication, interpolation, fixed input writing, and lifecycle reset
   explicit at the client composition point and cover it with schedule-trace tests.

The implementing milestone must verify the exact Bevy and Lightyear system sets before choosing the
final schedule labels. The required behavioral contract above is stable even if dependency versions
or specific integration set names change before this v2-or-later work begins.

## Navigation contract

Arena-bounds clamping alone is not sufficient: direct chase and retreat vectors can wedge a fighter
against permanent cover or loop around a chokepoint. When the replicated map identity changes, the
bot client derives a bounded deterministic navigation representation from `ResolvedMapSnapshot`:

- inflate collision geometry by fighter clearance;
- create or select stable-ID waypoints/portals around permanent geometry;
- determine line-of-travel and line-of-fire separately;
- choose paths and equal-cost alternatives using stable deterministic tie-breakers;
- steer locally for chase, desired-range, retreat, strafe, and objective approaches;
- detect lack of progress over a bounded tick window and deterministically replan.

This representation is pure client planning data, not collision authority. The server remains the
only owner of movement and collision outcomes. Dynamic terrain, hazards, surfaces, and concealment
must extend the observation/navigation contract when their future milestone makes them relevant;
they must not introduce hard-coded map coordinates.

## Policy design

The first policy is **hand-written utility AI with a small committed-duration tactics layer**. It has
no Bevy ECS dependency and does not require an AI framework.

- **Utility scoring chooses a tactic.** Candidate tactics such as `approach`, `hold_range`,
  `retreat`, `strafe`, and `contest_objective` are scored from validated curves over health,
  distance, line of travel, line of fire, objective pressure, observation age, and resolved build
  capabilities.
- **A small state machine holds commitments.** Strafe direction, retreat bursts, target locks,
  path/replan state, and reaction deadlines prevent frame-to-frame dithering. It does not duplicate
  the full behavior selection graph.
- **Combat actions are explicit decisions.** Primary fire, active-item use, ultimate use, aim
  direction, aim distance, and deployable placement are evaluated from delivery/ability
  capabilities. They are not generic readiness buttons or branches on build preset IDs.
- **Mode goals are adapters.** Wipeout supplies survival/pressure goals; Hot Zone supplies contest,
  defend, and displacement goals. The common tactic scorer consumes bounded goals instead of
  embedding mode branches throughout movement and combat code.
- **Behavior trees remain deferred.** With one code-first profile, a tree framework adds
  indirection. A later tree or learned policy may consume the same observation and emit the same
  decision shape.

The boundary is a deterministic state transition rather than a function that mutates hidden RNG and
tactic state:

```rust
fn decide(
    observation: &BotObservation,
    state: BotTacticState,
    entropy: BotEntropy,
    profile: &BotProfile,
) -> BotDecision
```

`BotDecision` contains the next tactic state, ordinary `FighterInput`, selected stable target/path
identities, chosen tactic, and a bounded diagnostic reason. Diagnostics support tests and local
tuning but are not sent as bot-specific gameplay protocol messages.

## Profile and deterministic entropy

Ship one code-owned, validated `BotProfile` containing utility curves and bounded values for desired
ranges, reaction delay, aim error, commitment duration, observation staleness, navigation clearance,
and stuck detection. Treating this as typed data prevents scattered magic constants; it does not
create player-facing difficulty selection or authored gameplay content.

Use a project-owned `BotRng` with a pinned, documented PCG32 algorithm and algorithm/version tag, so
reproducibility does not depend on a transitive crate or platform RNG. Derive independent entropy
streams for build choice, target tie-breaking, tactics, aim error, and timing from:

```text
explicit bot seed + match ID + local life generation + observed authoritative tick + stream ID
```

Generate a fixed `BotEntropy` sample set for a decision before evaluating conditional branches.
Adding a new random choice to aiming must not shift later navigation or tactic choices. The default
explicit seed may be derived from `--client-id` for local convenience, but logs and test artifacts
must report the effective seed, algorithm version, profile version, match ID, and life generation.

## Lifecycle and client configuration

Bot mode must be distinct from finite process-verification automation. Prefer one explicit run-mode
configuration over additional interacting booleans:

```text
ClientRunMode
  Interactive
  Verification(HeadlessAutomationConfig)
  Bot(BotConfig)
```

`--bot` selects `Bot` mode and implies headless composition. It is mutually exclusive with
verification overrides such as `--move-axis`, `--aim-axis`, `--aim-dummy`, `--fire`, `--ultimate`,
and `--simulation-ticks`. `--bot-seed <u64>` is optional. `--build-preset` selects an explicit legal
build; otherwise the build-choice entropy stream selects from supported built-in presets sorted by
stable preset ID. Custom build selection is never synthesized implicitly.

Bot mode does not inherit the current `--headless` requirement for `--exit-after-roster`. By default
it remains connected across match restart until the server disconnects or the process receives
normal shutdown. A future implementation may add an explicit bounded match-count exit option for
automation, without coupling policy decisions to verification tick limits.

Auto-selection, ready, and restart use the existing reliable idempotent session transactions. They
are enabled by `Bot` run mode rather than by `headless_simulation_ticks`. Rejection, timeout,
disconnect, server shutdown, countdown cancellation, active forfeit, and restart retain the ordinary
client outcomes and must never spin or silently hang.

Use a local lifecycle key consisting of match ID and a monotonic observed life generation. On defeat
or respawn waiting, immediately emit neutral input. Construct fresh tactic/navigation state once on
the transition back to a living fighter; do not reset independently on both defeat and respawn.
Changing match ID resets all match-scoped state and derives new entropy streams.

## Suggested ownership

Keep the implementation private under a cohesive client-owned module rather than growing
`client/input.rs`:

```text
client/bot/
  mod.rs          plugin composition and narrow exports
  observation.rs  ECS-to-owned observation allowlist and canonical ordering
  navigation.rs   map-derived graph, path selection, steering, stuck recovery
  policy.rs       utility scoring and deterministic state transition
  profile.rs      validated profile and version
  entropy.rs      pinned RNG and independent streams
  lifecycle.rs    run-mode session, match, and life integration
```

The ordinary input writer remains the sole bridge from local intent to Lightyear
`ActionState<FighterInput>`. In-process test clients install the same bot plugin and observation
adapter; they do not call a second server-facing policy path.

## Verification requirements

A future bot milestone must include:

- pure transition and golden tests for canonical synthetic observations;
- invariants proving all emitted axes/distances/buttons are finite, bounded, and neutral for stale,
  incomplete, dead, respawning, non-active, or no-target observations;
- deterministic ordering/tie tests with ECS insertion and observation collection orders permuted;
- entropy-stream tests proving an added draw in one stream does not perturb another;
- fixed-schedule traces proving at most one decision per observed authoritative generation and the
  required ordering before input writing;
- navigation tests for every supported map, including cover, chokepoints, equal-cost paths, blocked
  goals, and bounded stuck recovery;
- build-capability tests for straight, lobbed, melee, Dash, Sentry, and later supported primitives;
- mode-goal tests for every supported mode rather than only nearest-enemy combat;
- lifecycle tests for selection, ready, countdown cancellation, defeat, respawn, forfeit,
  completion, restart, rejection, timeout, disconnect, and clean shutdown;
- separate-App/Crossbeam authority tests proving the policy sends only ordinary client intent;
- real subprocess/UDP tests under local, typical, and adverse impairment profiles;
- repeated-match and long-running soak tests for bounded state, diagnostics, and entity cleanup;
- future concealment tests proving hidden state cannot reach `BotObservation`;
- human playtests evaluating readability, aim imperfection, retreat telegraphing, objective behavior,
  build matchups, and whether the bot is fun rather than merely effective.

Exact network-session traces are not golden determinism tests. Record the effective seed and
canonical observation/decision trace when a failure needs deterministic policy replay.

## Deferred and non-goals

- Assigning bots to a milestone before a future version is scoped.
- Lobby fill detection, matchmaking, in-match backfill, or server subprocess orchestration.
- Player-facing difficulty presets, skill ranking, adaptive difficulty, or automatic balance tuning.
- Bot identity, bot-only protocol messages, or bot-specific server authority rules.
- Learned-policy training, replay datasets, inference runtimes, or remote policy services.
- A generic public bot SDK before an external consumer demonstrates the boundary.
- Behavior-tree or utility-AI dependencies while the focused policy remains maintainable.

Anything outside the official client that later speaks the protocol must still implement Brawler's
compatibility/content handshake, session transactions, native input buffering, replication rules,
and versioned observation semantics. Protocol compatibility alone does not make an implementation a
supported bot client.
