# Bots

## Decision

Bots that fill in as players are **external clients**, not server-internal entities and not a
separate offline simulation. A bot is the existing macOS client application launched in a
headless bot mode: it connects over the real network transport, joins, selects a build,
readies, and plays the match by sending ordinary `FighterInput` intent through the same
validated path as a human player. The dedicated server treats a bot exactly like any other
client and contains no bot-specific simulation code.

This decision was reached after comparing three approaches:

1. **Server-internal bots** — the server writes `FighterInput` for fighters without a
   connection. Cheapest per-tick and deterministic, but the bot reads authoritative state
   directly, so fairness would depend on hand-tuned handicaps instead of architecture, and
   the `ControlledBy` input-ownership rule would need a bypass path.
2. **External client bots (chosen)** — a bot is a client whose input is generated by a
   policy instead of a device. Chosen because:
   - **Architectural fairness for free.** A bot consumes only the replicated, interpolated
     stream — exactly what a human sees. No hidden-state access to design around.
   - **The validation gauntlet applies.** Bot input flows through ownership checks, rate
     limits, and freshness neutralization. Bots cannot misbehave on the wire by
     construction, and the "same server-authoritative simulation path" product rule holds
     with zero server changes.
   - **Technology openness.** Anything that speaks the netcode protocol can be a bot. A
     later learned policy or non-Rust bot needs no game-server changes.
   - **Most of the machinery already exists.** Headless mode already auto-selects a build,
     auto-readies, and drives input (`apply_headless_input`); a bot generalizes this into a
     pluggable policy.
3. **Learned policies (ML/imitation)** — deferred. No replay dataset, evolving gameplay,
   and the product values readable combat over optimal play. The policy interface from (2)
   keeps this door open.

## Scope for the first version

- **Launch via CLI** (or a thin launch recipe script alongside the existing
  `network-match.sh`), because there is no lobby or fill UI yet: whatever connects is a
  player. The server does not spawn or manage bot subprocesses in this version; that is a
  possible future iteration, deliberately unspecified now.
- **One hand-tuned behavior profile.** No difficulty presets — ranking bot skill is
  premature while gameplay itself is evolving. The tuning target is *fun to fight*: a bot
  that misses sometimes, telegraphs its retreats, and does not perfectly track projectiles
   reads as an opponent rather than an aimbot. This is playtest-driven tuning, not a data
  model.
- **Seeded decisions.** The policy uses an explicit seeded RNG (per the roadmap
  determinism rule) so a bot session is reproducible in isolation, even though an external
  wall-clock process is not tick-reproducible against the server.

## Shape

```text
bot client (headless, CLI-launched)
  policy: pure function from observed replicated state → FighterInput
          (chase/retreat/strafe, aim error threshold + reaction delay,
           ability readiness heuristics, arena-bounds awareness)
          ↓
  existing client input path → network → server validation → authoritative sim
```

The policy is the only substantial new code. Join, build selection, readiness, combat,
scoring, and replication are unchanged. Automated network tests reuse the same policy
in-process (harness-style bot clients) where tick-deterministic assertions are needed.

## Non-goals for now

- Server-side fill detection or subprocess orchestration.
- Difficulty presets or skill ranking.
- Bots as match participants beyond what the ordinary client join path already provides
  (unlike fixed test dummies, which do not count as participants).
- Any bot-specific protocol messages or server-side bot awareness.

## Tech stack decision

The bot policy is **hand-written utility AI with a small committed-duration tactics layer** —
no AI framework or crate.

- **Utility scoring decides.** Candidate actions (`chase`, `keep_distance`, `retreat`,
  `strafe`) are scored each tick from curves over health, distance, aim error, and ability
  readiness; the highest score wins, with hysteresis and seeded score noise so choices do
  not flip-flop. Fire and ability use are gates layered onto the winning movement action,
  not separate states. Continuous tradeoffs match arena combat, "fun to fight" tuning is a
  number in one place, and future difficulty presets would simply be curve parameters.
- **A tiny FSM holds committed tactics.** Strafe-direction hold ticks, retreat bursts, and
  reaction-delay timers live in a small tactic state so movement does not dither. It is not
  the decision-maker; an FSM over the full behavior set would multiply states as gameplay
  evolves.
- **Behavior trees are deferred.** They pay off with many behaviors, priority interactions,
  and visual editing by non-programmers. With one code-first profile they are indirection.
  The utility scorer can later be refactored into tree leaves without changing the policy
  boundary.
- **big-brain is rejected for now.** It is the idiomatic Bevy utility-AI crate, but the
  project has moved to Codeberg with no release for about a year and remains pinned to
  Bevy 0.15, while Brawler is on Bevy 0.19 via Lightyear 0.29. It would also make the
  policy an ECS-participating system, weakening the pure-function property below. Revisit
  only if the hand-rolled scorer grows painful and the crate tracks current Bevy.

The policy is a pure function with no ECS dependency, so it is unit-testable with synthetic
observations and reusable in-process by automated network tests:

```rust
fn decide(obs: &BotObservation, state: &mut BotTacticState, rng: &mut SeededRng) -> FighterInput
```

- `BotObservation`: borrowed replicated state (own health/weapon/ability, enemy poses,
  projectiles, arena bounds).
- `BotTacticState`: hysteresis and committed tactics (strafe hold, retreat commitment,
  reaction timer, last-chosen action).

No new dependencies are introduced for the bot.

## Resolved questions

- **CLI shape.** `--bot` is a distinct client mode, not another headless behavior override.
  It implies headless, auto build selection (honoring `--build-preset` if given, otherwise
  a seeded preset pick), auto ready/restart, and routes input through the policy. It is
  mutually exclusive with `--move-axis`, `--aim-axis`, `--aim-dummy`, `--fire`, and
  `--ultimate`, validated like the existing headless-flag checks. `--bot-seed <u64>` is
  optional and defaults to a seed derived from `--client-id`, so multi-bot launches differ
  but remain reproducible.
- **Launch recipe.** A new `scripts/network-bots.sh` reuses the build/ready-file pattern
  from `network-match.sh` and launches a configurable number of bot clients (plus any
  human client the user starts). `network-match.sh` stays a verification gate with its
  existing dumb-override clients and report assertions; switching it to `--bot` clients is
  optional follow-up, not part of this design.
- **No-enemy and non-active phases.** The policy is phase-aware: when the match is not in
  the active phase, or no living enemy is observable, it emits neutral `FighterInput`
  (zeroed axes, no buttons — no attack-economy waste during countdown). `BotTacticState`
  resets when the bot's own fighter is defeated or respawns, so committed tactics and
  reaction timers never carry across lives.
