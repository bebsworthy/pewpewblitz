Found during BRL-xtbw. src/server/mod.rs process_match_loading_messages currently requests AppExit::Success two seconds after terminal loading failure, without the supervisor Stop/Exit handshake. A worker whose client never checks in therefore exits code 0 and is classified WorkerExitMismatch. The successful Practice and diagnostic handoff causes are fixed by BRL-xtbw; this ticket owns failure-path cleanup. Preserve the readiness deadline and authoritative cancellation/requeue outcomes. Reproduce missing-client and rejected-readiness cases, retire routes and allocations through existing bounded control lifecycle, verify lobby remains usable and genuine crashes retain failure classification. No timeout relaxation or protocol change without separate evidence. Add lifecycle regression and native/automated cancellation evidence.

# Implementation (2026-11-19, with BRL-5yss)

## Research
- `process_match_loading_messages` (`src/server/mod.rs`) set `terminal_failure` on the 20 s readiness deadline, an accepted Cancel Match Start, or `StartFailed`, queued `CancelActivation`/`StartFailed`, and 2 s later wrote `AppExit::Success` directly. No Unlink, no `Exit`, so `reconcile_reaped` (`packages/brawler-routing/src/supervisor/process.rs`) saw success + `worker.exit == None` and logged `WorkerExitMismatch`.
- The supervisor's `forward_cancel_activation` / `forward_start_failed` (`runtime/control_io.rs`) only fan out `ActivationDissolved`; nothing sends Stop.
- The supervisor already accepts a worker `Exit` that no Stop preceded: `process_control_frame` checks role, zero terminal peers/queue bytes and `result_sent`, not the lifecycle phase, and `reconcile_reaped` classifies success + `Exit(category 0)` as `Stopped { forced: false }`. Reaping already runs `cleanup_worker` + `reclaim_terminal_allocations` (routes, capabilities, allocation record, seat release).
- `ProcessSupervisorConfig::graceful_stop` is 2 s, the same as the client-notice grace.

## Decision: worker-owned Exit after unlink (not supervisor Stop on CancelActivation/StartFailed)
- The 2 s grace exists so `TerminalFailure` and the cancelling client's `CancellationAccepted` reach clients (the cancelling client's outcome is sent one frame after the cancel). A supervisor Stop sent on `CancelActivation` arrives one IPC round trip later and immediately unlinks every peer, racing those notices; deferring Stop admission in the worker for 2 s would hit the 2 s graceful-stop deadline and be force-killed.
- So the worker keeps the deadline, grace and cancellation/requeue outcomes unchanged, then calls `MatchControlOutbox::retire()`. `worker_control_receive` begins retirement only after every queued activation fact (`StartFailed`/`CancelActivation`/`Activated`) has entered the control stream, through `begin_ordered_shutdown` — the same path an admitted Stop takes: Unlink all peers → `worker_control_finish_shutdown` queues `Exit` (category 0, `result_sent=false`, zero peers/queue) once peers and queues are drained (and after the cancel frame has flushed) → `worker_control_flush` writes `AppExit::Success` only after Exit left the writer.
- Still bounded: heartbeats stop once shutdown starts, so a worker that hangs during retirement is failed by the supervisor's 5 s heartbeat timeout. No protocol bytes, timeouts or classifications changed. `pending_stop` was redundant with `shutdown_requested && !exit_sent` and was removed; `queue_exit` no longer takes the StopBody.
- An unrouted app (no `MatchControlOutbox`, no supervisor) still exits directly.
- Lobby-originated `CancelActivation` still only dissolves the activation on the match worker; it then retires on the readiness deadline through this path. Not changed here.

## Feedback disposition
- 5yss plan option 1 (Exit after unlink): implemented. Option 2 (supervisor Stop on CancelActivation/StartFailed): rejected; it races the client-notice grace (see Decision).
- Lobby-originated CancelActivation does not retire the match worker early; it waits for the readiness deadline. This is pre-existing and out of scope, and not filed.

## Learning
- When a supervisor-owned shutdown and a worker-owned notice grace have the same 2 s bound, deferring the supervisor's Stop is not an option. Reusing the worker's ordered Exit path keeps both.
- Supervisor logs carry ANSI colour codes. The first freeze trigger grepped for `route="match"` and never matched, so the missing-client run had to be repeated. Grep for a token that the colouring does not split.
